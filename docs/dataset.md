# 数据集说明

## 为什么不能用计划书里写的 Last.fm

计划书 6.1 写「使用 Last.fm 公开数据集提供歌曲、歌词、用户行为数据」。实际核查后发现：

- Last.fm 360K / LFM-1b 这类公开数据集，内容是**收听事件**（user–artist–track–timestamp）
  加上**社交标签**，以及歌手/曲目的文本名称；
- 它**不包含任何音频文件**，也**不包含歌词文本**；
- 也就是说，REQ005 要求的「音频特征 + 歌词文本特征」无法从这份数据里直接得到。

所以数据方案必须调整。以下三条路径按推荐程度排列。

---

## 路径 A（默认，已实现）：合成演示集

```powershell
.venv\Scripts\python.exe scripts\prepare_data.py --count 600
```

脚本用 numpy 合成 600 段 6 秒音频，8 种风格（流行/摇滚/民谣/电子/爵士/古典/嘻哈/金属），
每种风格在速度、谐波数量、失真、噪声、和弦结构上各不相同，因此 MFCC 特征可区分。
歌名、歌手、专辑、风格标签、曲目描述由脚本按模板生成。

- 优点：零依赖、离线可跑、数据规模可控、可完全复现（随机种子固定）。
- 缺点：不是真实音乐，音频听感很"合成"。
- **使用要求**：报告与答辩中必须写明「音频为合成数据，用于验证系统链路」，
  不能表述为真实音乐库。

## 路径 B（推荐换成真实音频）：FMA-small 或 GTZAN

| 数据集 | 规模 | 内容 | 适合原因 |
| --- | --- | --- | --- |
| FMA-small | 1064 首，30 秒 | mp3 + 曲目元数据 CSV（含 genre_top、title、artist、album） | CC 授权清晰、风格标签现成、体量 1GB 左右 |
| GTZAN | 1000 首，30 秒 | wav + 10 类风格 | 最经典的音乐风格数据集，特征实验常客 |
| MTG-Jamendo | 更大 | 音频 + 情绪/乐器标签 | 标签更丰富，文本模态信号更强，但体量大 |

接入步骤（以 FMA-small 为例）：

1. 下载 `fma_small.zip` 与 `tracks.csv`（FMA 官网需勾选同意条款）；
2. 解压到 `D:\fma_small\fma_small`，目录结构形如 `fma_small\000\000002.mp3`；
3. 运行导入（`--meta` 指向 FMA 的 `tracks.csv`，脚本会读取 title / artist / album / genre_top）：

```powershell
.venv\Scripts\python.exe scripts\prepare_data.py --mode import `
    --src D:\fma_small\fma_small --meta D:\fma_small\tracks.csv
.venv\Scripts\python.exe scripts\load_tracks.py --reset
.venv\Scripts\python.exe scripts\build_features.py --force
.venv\Scripts\python.exe scripts\train.py
```

> 注意：FMA 的 `tracks.csv` 字段名与本项目的字段不完全一致（genre_top、title、artist、album）。
> `scripts/prepare_data.py` 的 `scan_import` 已做了兼容映射；如果字段名不同，
> 改 `scan_import` 里那一处 `m.get(...)` 即可，业务代码不需要动。

## 路径 C：自建歌单

把任意 wav/mp3/flac 放进一个目录，直接 `--mode import --src <目录>`。
没有元数据时，脚本会用文件名当歌名、风格标为「未分类」，之后可在后台上逐个补全。

## 关于歌词

结论：**本项目不追求真歌词，文本模态使用「曲目元数据 + 风格标签 + 曲目描述」**。理由如下：

1. **版权与合规**：中文歌词的公开可用语料很少，多数是爬取产物，课程项目里引用有风险。
2. **可获得性**：FMA / GTZAN 均不含歌词；强行让歌词与音频逐首对齐，成本远高于它的收益。
3. **效果边际**：文本模态的作用是提供"内容语义"信号。风格标签 + 情绪/乐器描述已经能区分
   流行/金属/古典这类语义差异，对推荐排序的贡献与真歌词在同一量级。

如果老师明确要求"必须用歌词"，两条可行补充方案：

- 用公开的多语言歌词数据集（如 Lyrics 类公开语料）只做**文本模态**，音频仍用 FMA；
  两边通过"风格 + 歌名"做弱对齐，允许部分歌曲没有歌词（`lyric` 字段留空即可）。
- 退一步：让队友写 100 首左右的**人工描述**（每首两三句），当作文本语料。
  这在课程答辩里是站得住的做法：明确声明"文本模态语料为人工标注的曲目描述"。

代码上不用改结构：`recsys/features.py` 的 `build_text_corpus` 已经会把
`music_name / singer / album / style_tag / description / lyric` 拼在一起，
只要数据库里 `lyric` 有值，就会自动进入文本特征。

## 用户行为数据

没有真实用户，因此用 `scripts/seed_simulated.py` 按「风格偏好画像」模拟：

- 300 个模拟用户，每人 1 个主风格标签、60% 概率带 1 个次风格；
- 点歌概率 = 风格匹配权重 × 热度（长尾扰动）× 随机数；
- 交互条数 8~120 条，其中 40 个「新用户」只有 0~2 条（用于观察冷启动）；
- 约 10% 的播放转成收藏。

生成的规模约为 1.3 万条播放记录、1300 条收藏。

**必须在报告中声明这是模拟数据。** 如果后续拉到真实测试用户（哪怕只有 20 个人），
把这些行为写进 `user_play_history` 后重跑训练即可，代码不用改。

## 数据规模建议

| 项目 | 建议值 | 说明 |
| --- | --- | --- |
| 歌曲数 | 300 ~ 1500 | 600 首足够跑出稳定结论，超过 2000 首后提特征时间明显变长 |
| 用户数 | 200 ~ 500 | 少于 100 个用户时，门控网络的用户侧信号太弱 |
| 交互数 | 1 万 ~ 5 万 | 低于 5000 条时 BPR 训练容易过拟合 |

本机实测：600 首音频提特征约 3 分钟（4 进程），训练 30 轮约 40 秒（CPU）。
